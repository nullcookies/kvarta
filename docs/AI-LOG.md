# Лог работы с ИИ

Проект делался агентом (DeepSeek Harness + субагенты) под управлением человека.
Ниже — настоящий процесс: что поручалось ИИ, где он ошибся, как это заметили и
что переделали руками. Без причёсывания.

## Как была устроена работа

- **Один ведущий агент** держит план, инфраструктуру (DDEV, Composer, Drush,
  WordPal, Canvas CLI), пишет бэкенд формы и принимает решения по архитектуре.
- **Три субагента параллельно** собирали Canvas-компоненты по согласованному
  контракту (`docs/CANVAS-DECOMPOSITION.md`): базовые элементы, контентные
  секции, форма и «обвязка». У каждого — свой список файлов, чтобы не
  конфликтовать.
- **Скиллы** (drupal_devkit → маркетплейс `drupal-canvas-plugin`, плюс скиллы
  стартера Canvas: `canvas-design-decomposition`, `canvas-component-definition`,
  `canvas-component-metadata`, `canvas-styling-conventions`) читались агентами
  до начала работы и определяли контракт компонентов.

## Журнал эпизодов

### 1. Первый запуск DDEV упал в песочнице — и это оказалось не DDEV

`ddev version` и `docker version` падали с `permission denied` на именованном
канале Docker. Первая гипотеза — «Docker Desktop не запущен». Проверка
показала: Docker Desktop работает, а доступ режет файловая песочница сессии.
Вне песочницы Docker 29.8.2 и DDEV v1.25.2 отвечают нормально.
**Вывод:** прежде чем чинить инструмент, надо убедиться, что сломан именно он.

### 2. `ddev config` перезаписался поставкой Drupal CMS

Я создал DDEV-проект `kvarta`, а `ddev composer create-project drupal/cms`
принёс свой `.ddev/config.yaml` (без имени проекта). DDEV увидел конфликт:
«Project 'test1' ... already used by project 'kvarta'» и отказался стартовать,
из-за чего `ddev composer install` вообще не выполнился.
**Как поймали:** шаг `ddev composer install` вернул ошибку старта, которой в
обычной ситуации быть не должно.
**Починка:** в конфиг из поставки добавлены `name: kvarta` и `php_version: 8.4`;
hooks поставки (composer install + `drupal:recipe-unpack`) сохранены как есть.

### 3. Composer повис на post-start-хуке, и агент его убил

`ddev start` выполняет post-start-хук с `composer install`. Хук шёл больше
20 минут без вывода (PowerShell буферизовал поток через `Select-Object`),
и это выглядело как зависание. Агент снял задачу и запустил composer руками.
**Ошибка агента:** убийство процесса-обёртки не убило composer внутри
контейнера; две установки пошли одновременно и начали «драться» за
`vendor/` (размер каталога скакал 135 МБ → 98 МБ → 37 МБ).
**Как поймали:** посмотрели `ps` внутри контейнера вместо консольного вывода —
увидели и живой composer, и `rm -rf` его временных каталогов.
**Починка:** дождались завершения одной установки; повторный
`ddev composer install` отчитался «1 install, 0 updates, 0 removals»
(ставился только `drupal/core 11.4.10`).
**Причина медленности:** DDEV 1.25 на Windows работает на bind-mount без
Mutagen, распаковка 230+ пакетов идёт через границу файловой системы.

### 4. ИИ поставил точку с запятой не в том месте — Canvas это поймал

Субагент сделал `section` с пропом `paddingY` и подписью `Vertical Padding`.
Собственный валидатор Canvas требует, чтобы id пропа был camelCase от подписи
(`verticalPadding`). Валидация упала на `section/component.yml`.
**Важно:** субагент не стал самовольно менять контракт, а вернулся с вопросом —
это правильное поведение. Решение принято человеком-постановщиком (ведущим
агентом): id переименован в `verticalPadding`, контракт и документ обновлены,
потребителей ещё нет, поэтому переименование бесплатное.

### 5. Тот же валидатор заставил переименовать подписи CTA в hero

`Primary Button Text` давал id `primaryButtonText` вместо контрактного
`primaryText`. Субагент сохранил id по контракту и поменял подпись на
`Primary Text` — верный компромисс: правило Canvas про id важнее косметики
подписи.

### 6. Мелочь, которую ИИ заметил сам

В примерах стартера у `heading` был проп `textShadow`, но классов
`text-shadow-*` в теме нет — то есть проп ничего не делал. Субагент это
обнаружил, удалил и доложил. Такую «мёртвую» настройку легко было бы
протащить в прод незамеченной.

### 7. Локальная проверка против проверки «в живом сайте»

`npx canvas validate` ругался на все компоненты сразу: «API endpoint not found:
/oauth/token» — сайт ещё не был установлен. Агенты научились разделять
локальные проверки (линт, схема `component.yml`, сборка Tailwind) и проверку
target-site, и не пытались «починить» компоненты из-за отсутствующего сайта.

### 8. Кнопка, которая пропала: конфликт нелейерного CSS (нашёл Lighthouse)

Первый замер Lighthouse показал Accessibility 86 и четыре нарушения
контраста, а на скриншоте заголовок первого экрана вообще не читался: белый
текст с классом `text-white` рендерился тёмным. Причина оказалась
архитектурной: тема, сгенерированная WordPal из WordPress, подключает свой CSS
**без `@layer`**, а по спецификации CSS нелейерные правила сильнее любых слоёв —
поэтому цвета темы перебивали Utility-классы Tailwind. Человек бы это увидел
глазами, но именно отчёт Lighthouse дал точный список из четырёх мест.
Починка: приоритетный блок в `canvas/src/global.css` + токен
`--color-accent-ink` для мелкого карамельного текста на светлом фоне.
Итог: контраст 0 нарушений, Accessibility 90, SEO 100.

### 9. `+=` вместо присваивания в конфиге метатегов

Скрипт OG-превью дописывал теги через `+=`, а в поставке Drupal CMS эти ключи
уже заданы токенами — `+=` не перезаписывает существующие ключи. В итоге
`og:image` молча не появлялся: тег оставался токеном, ссылающимся на пустое
медиаполе страницы. Заметили по выводу проверки метатегов, а не по коду.

### 10. Агент сам нашёл, что его проверка врёт

В браузерном сценарии форма «не показывала результат», хотя на скриншоте ответ
уже был. Оказалось, в Playwright у селектора `text=` нет альтернации: строка
`text=Спасибо|уже приняли` искалась буквально целиком. Исправили на
regex-синтаксис — и сценарий стал зелёным. Это к вопросу о том, что
«упавший тест» не всегда означает сломанный продукт.

### 11. Флаки-шаг публикации

`canvas push` несколько раз обрывался на шаге подготовки страницы с
«No response from https://kvarta.ddev.site»: контейнер на Windows-бинмаунте не
успевал отвечать. Компоненты и ассеты при этом уже выгружались. Пришлось
сделать повторные попытки — и записать это в README, чтобы следующий человек
не искал ошибку в компонентах.

### 12. Лекарство оказалось хуже болезни (приоритетный блок и цвета фактов)

Борясь с нелейерным CSS темы, агент добавил в `global.css` блок цветовых
утилит с `!important`. Контраст кнопок и заголовков это починило, но сломало
другой приём: подписи фактов красились родителем через селектор
`[&_.fact-item-label]:text-primary-200`, а прямой класс с `!important` на самом
элементе оказался сильнее. На тёмном фото подписи стали тёмно-коричневыми
(`rgb(98, 81, 60)` вместо светлого).

Заметили не по коду, а по замеру: скрипт
[canvas/scripts/dev/inspect-element.mjs](canvas/scripts/dev/inspect-element.mjs)
показал фактический вычисленный цвет элемента в живом браузере. Починка —
перестать полагаться на наследование: у `fact-item` появился собственный проп
`textColor`, и цвет объявляется прямым классом на элементе. Урок записан в
README: в этом проекте наследование цвета и селекторы-потомки ненадёжны.

### 13. Preload, который молча ничего не делал

При доработке SEO агент добавил в `kvarta_seo` preload hero-картинки
(`fetchpriority=high`). Тег не появлялся в HTML, но и ошибок не было. Причина
оказалась коварной: код проверял `$entity instanceof CanvasPageInterface`, а
такого интерфейса в Canvas **не существует** — есть
`ComponentTreeEntityInterface`, который и реализует `Page`. `instanceof` с
несуществующим типом не падает, он просто всегда возвращает `false`, поэтому
вся ветка preload молча не выполнялась. Вторая половина бага: front-страница
искалась регуляркой по `/canvas_page/`, хотя внутренний путь Canvas-страницы —
`/page/{id}`.
**Как поймали:** не по коду, а по факту — в отчёте проверки preload-ов было
`0` вместо ожидаемых. Пришлось распечатать финальный HTML и сверить.
**Починка:** `instanceof ComponentTreeEntityInterface`; определение главной —
через `router.no_access_checks->match('/')` и параметр `canvas_page` вместо
регэкспа. Урок: опечатка в имени интерфейса не даёт ошибки, только «тихое»
отключение функциональности — такие места надо проверять наблюдаемым
результатом (тег в HTML), а не тем, что «код выглядит правильно».

### 14. Меню, которое Lighthouse не считал списком

После добавления `<main>` лендмарка Accessibility поднялся до 92, но остались
нарушения `list`/`listitem`. Причина — в устройстве слотов Canvas: `<ul>` в
компоненте `nav-links` получает прямыми детьми `<astro-slot>` (обёртки слотов),
а `<li>` из `nav-link` оказывается внутри слота, а не внутри `ul`. Семантически
вложенный список через Canvas-слоты собрать нельзя.
**Починка:** в `nav-links`/`nav-link` заменили `<ul>`/`<li>` на `<div>` —
классы `flex`/`gap` сохранены, визуально ничего не поменялось, лендмарк `<nav>`
остался. Accessibility 92 → **100**.

### 15. robots.txt из конфига — плата флаки-аудитом

`robots.txt` перевели с физического файла на конфиг модуля `robotstxt`, чтобы
ссылка на карту сайта (`Sitemap:`) не терялась при рекомпозиции scaffold.
Побочный эффект: файл теперь отдаётся через бутстрап Drupal, и в медленном DDEV
Lighthouse иногда не успевает его скачать — итоговый SEO падает только на
аудите `robots-txt` с пояснением `Timed out fetching resource`. Это таймаут
загрузки, а не поломанный файл; поведение и обход описаны в
[docs/LIGHTHOUSE.md](LIGHTHOUSE.md), повторный прогон даёт SEO 100.

### 16. Маска телефона, которая ломала номер при вставке

При добавлении маски `+375 (29) 123-45-67` агент сделал две вещи: на фокус в
пустое поле подставлял префикс `+375 `, а при вводе вычищал из значения всё,
кроме цифр, и снимал ведущий код страны одной заменой `replace(/^375/, '')`.
Сам по себе код выглядел правильно, ручной ввод по одной цифре работал.
Но браузерная проверка формы стабильно падала с подсказкой «Такого кода
оператора в Беларуси нет».
**Как поймали:** по факту, а не по коду. В отчёте проверки вместо сообщения об
успехе приходила ошибка, а номер, который вводили (`+375 (29) 276-50-76`),
превращался в `+375 (37) 529-27-65` — цифры «поехали».
**Причина:** префикс подставляется на фокус, а вставка номера происходит уже
после него — в поле оказывалось `+375 375292765076`. Функция снимала только
один ведущий `375`, оставшийся код страны уезжал в национальную часть и менял
её целиком. Это не артефакт автотеста: человек, щёлкнув в поле и вставив
скопированный номер, получил бы тот же сломанный номер.
**Починка:** снимаем ведущий код страны в цикле — пока строка начинается на
`375` и остаётся длиннее 9 цифр. Национальный номер Беларуси не начинается на
`375`, поэтому лишнее вхождение — гарантированно код страны. Урок: у маски или
нормализатора ввода мало проверить, что «код выглядит верным», — надо прогнать
вставку и стирание разделителей в реальном браузере.

### 17. Отступы hero, которых снаружи не было

Задача — растянуть картинку hero на всю ширину блока. Замер показал: при
viewport 1440 секция hero занимает 1152 с отступами по 144 слева и справа.
Выглядело так, будто контейнер задаёт что-то снаружи.
**Как поймали:** замером `getBoundingClientRect()` по самой секции и её
родителям. У обёрток Canvas (`canvas-island`, `astro-slot`) прямоугольник
нулевого размера — мерить по ним бессмысленно; реальную геометрию задавала
**внутренняя** обёртка компонента `section` с
`max-w-(--container-content) px-4 md:px-6`.
**Починка:** добавили в `section` вариант `width: full` (`max-w-none px-0`),
боковые паддинги переехали в варианты `normal`/`wide`, у hero в спецификации
страницы `width` → `full`. Проверка: `hero.width` = 1440 = viewport. Урок: в
Canvas геометрию считают реальные компоненты, а обёртки-острова нулевые —
источник вёрстки надо искать в первом непустом узле.

## Что человек решил сам (не отдано ИИ)

- Выбор архитектуры: Drupal CMS + Canvas Code Components вместо Next.js,
  шаблон The Coffee Shop вместо Figma.
- Хранение заявок в таблице Drupal (а не в файле/SQLite) с обоснованием.
- Отказ от публичного хостинга: по требованию заказчика среда — локальный DDEV.
- Изменение контракта `section.verticalPadding` вместо правки подписи.
- Решение оставить Performance как есть и честно описать причину (нет SSR у
  Canvas-островов) вместо косметических правок вёрстки.
